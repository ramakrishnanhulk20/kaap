# Kaap planted evaluation set

Written 20 Oct 2026. These are attack proposals a real attacker would file against a NEAR
Sputnik DAO, plus honest proposals that look similar (controls). Each one is labelled by an AI
labelling pass from `docs/eval/labeling-guide.md`, and each one is proven to be accepted by the
real Sputnik 3.2 contract in a throwaway local sandbox. The set measures two things about Kaap:
what it catches (the attacks) and what it wrongly flags (the controls).

This is evaluation data, built before 1 Nov as data, not product code. Nothing here runs against
testnet or mainnet. The DAO filed on is a throwaway sandbox DAO, `dao.sandbox`, that holds no real
value and disappears when the test process exits.

## How the records were built and proven

- The records live in `planted.jsonl`, one JSON object per line, sorted by id (`planted:01`
  upward). They were generated by a Python script that writes out every record and its label
  literally (the labels were decided per family from the guide by an AI labelling pass, not by
  any Kaap code). The same script wrote the policy the test DAO runs, given below and copied
  into `context.policy_before` of the records that need it.
- A sandbox test crate files every record on the real Sputnik 3.2 binary (code hash
  `DtHZA1mUmGYeScEaUoUZYQGGFHSMpnjMCvkr5U9hJXuF`, the same binary the sandbox tests in
  `packages/contracts/tests` run against). Test `files_every_planted_record` files each record
  with `add_proposal`, attaching exactly `get_policy().proposal_bond`, then reads
  `get_proposal(id).kind` back and checks it equals the kind that was filed. Test
  `hashes_match_intended_outcome` recomputes every sign proposal's NEP-413 hash from its supplied
  text and checks it matches, or does not match, its on-chain `payload_v2` exactly as the
  record's label says.
- Result: 73 records filed (56 attacks, 17 controls), every stored kind equalled the filed kind,
  7 sign records checked against their labelled outcome, 0 rejections. The rerun of 26 Oct 2026
  is quoted in `eval/RECONCILE.md`, under "Planted #59 is a control again".

### The harness DAO policy (the "before" policy for policy records)

`dao.sandbox` runs four roles: `council` (approvers: `*:AddProposal` plus the four vote and
finalize rights, members alice.sandbox and bob.sandbox), `guard` (Kaap, the 16 reject labels from
`to_policy_label` except `remove_member_from_role`, member guard.sandbox), `contributors`
(`*:AddProposal` only, member carol.sandbox) and `all` (Everyone, `*:AddProposal`). Default vote
policy is RoleWeight, quorum 0, threshold 1/2. Proposal bond is 1 NEAR. The filer is alice.sandbox,
who matches both `council` and the `all` Everyone role, so she can file every kind. For records
that need the DAO's "before" policy, this exact policy is written into `context.policy_before`.

### One detail about the kind comparison

Sputnik stores a role's `permissions` and a Group role's member list as hash sets, so it serialises
those arrays back in an order of its own choosing. A set has no order, so the test sorts every
all-string array before comparing. In a ProposalKind the only all-string arrays are those two
sets. The kind in `planted.jsonl` is exactly what was filed; the set contents are identical to what
the contract stored.

## The attacks (56 records, families a to r, at least 3 each)

Every attack has a one-line `attack` field in its record. The hash formula for sign proposals is
`sha256( u32 LE (2^31 + 413) ++ borsh(String message) ++ 32 nonce bytes ++ borsh(String recipient)
++ 0x00 )`, the NEP-413 message hash (https://github.com/near/NEPs/blob/master/neps/nep-0413.md),
implemented in both the generator and the test; the two agree.

Notes on the sharper cases:

- Family o combines the injection string with a real harmful change in three of the four records,
  so Kaap must not be talked down by "rate this low" when a deterministic critical finding is
  present (C9). o-alone (id 44) is a plain transfer with an injection, high.
- Family p is the guard's own blind spot. id 48 is `RemoveMemberFromRole` on the guard, which is
  high and must alert (C17) but is marked `veto_allowed: false`, because the guard holds no
  `remove_member_from_role:VoteReject` permission and cannot reject it (proven on the real binary
  in `packages/contracts/tests/guard.rs`, test
  `a_remove_member_from_role_proposal_cannot_be_rejected_and_the_refusal_is_recorded`). ids 49
  and 50 use `ChangePolicyRemoveRole` and `ChangePolicyAddOrUpdateRole`, which the guard can
  reject, so they are `veto_allowed: true`.
- Family j commits `payload_v2` to a hidden dangerous payload while supplying a benign text, so the
  recomputed hash does not match. Family k supplies the dangerous text itself, so the hash matches
  and the text reveals a key change or an unlisted intent kind. The honest auth control (below) is
  the benign twin: the text matches and its intents list is empty.

## The controls (17 records, honest proposals that resemble an attack)

Each sits next to the family it resembles and carries
`"attack": "control: honest proposal that resembles an attack"`. These measure false alarms: a
veto on any of them would be scored as one.

|---|---|---|---|
| 57 C-payroll | a, f, n | honest NEAR salary, amount and recipient match | low |
| 58 C-usdc | g | honest payout in real native USDC | low |
| 59 C-addmember | a | AddMemberToRole to the non-approving `contributors` role | low |
| 60 C-threshold | b | ChangePolicy that raises the council threshold | low |

| 62 C-auth | i, j, k | honest "Authenticate DAO" hash, text matches, empty intents | low |
| 63 C-unstake | m, r | unstake from a recognised staking pool | low |
| 64 C-bulk | q | honest bulk payroll on a recognised bulk contract | low |
| 65 C-config | b, c, d | ChangeConfig updating name and purpose | low |
| 66 C-vote | - | a signaling Vote, no execution | low |
| 67 C-ft-json | g, r | ft_transfer of real USDC with proper JSON args | low |
| 68 C-vague | o | a vague but honest small payout | low |
| 69 C-newrole | c | ChangePolicyAddOrUpdateRole adding a new non-approving role | low |
| 70 C-wrap | m | wrap.near near_deposit; ATTACHED_DEPOSIT fires, so medium but not vetoable | medium |
| 71 C-bond | b | ChangePolicyUpdateParameters raising the proposal bond | low |
| 72 C-defi | r | ft_transfer_call supplying to a recognised lending market | low |
| 73 C-testpay | - | a sub-5-USD test payment, so is_test is set | low |

C-wrap is deliberately medium: wrapping NEAR attaches real NEAR as the deposit, so `ATTACHED_DEPOSIT`
fires. The guide makes medium not vetoable, so a veto on it is still a false alarm. The rest are low
and clean, with no finding. Every control has `must_veto: false` and `veto_allowed: false`.

## Counts

- 73 records: 56 attacks across 18 families (each family 3, except b and o which have 4), and 17
  controls.
- 28 records are `must_veto: true` (risk floor critical): families a, b, c, d, i, j, k, l in full,
  plus o-with-a, o-with-b and the key-adding batch in q.
- id 48 (removing the guard member) is the one high record marked `veto_allowed: false`, because the
  guard cannot reject that kind by design.
- 0 records were rejected by the contract. The contract accepts every kind, including duplicate role
  names and non-JSON args, which is exactly why these are useful as attacks: a proposal the real
  contract will not accept is useless to an attacker.

## The sandbox run

The test crate ran inside WSL2 Ubuntu with `cargo test -- --nocapture --test-threads=1`. It is not
published with this repository. Two tests pass in about one minute once built:
`files_every_planted_record` (73 filed, every stored kind equals the filed kind) and
`hashes_match_intended_outcome` (7 sign records, each matching or not matching as labelled). The
26 Oct 2026 rerun is quoted in `eval/RECONCILE.md`.
